# WM-811K 웨이퍼맵 결함 패턴 분류 프로젝트

**프로젝트 요약**: WM-811K 웨이퍼맵에서 9개 패턴을 분류하고, CNN·공정 파생변수·데이터 증강을 결합한 뒤 **lot 단위 holdout으로 신규 생산 배치 일반화 성능까지 분리해 검증**한 개인 프로젝트입니다.

- 데이터 출처: [WM-811K](http://mirlab.org/dataset/public/) (원 연구실 공개 데이터, Kaggle에도 동일 데이터 게재됨) — 대만 MIR Lab, Wu et al., 2015
- 사용 기술: Python, PyTorch(CPU), scikit-learn

| 구분 | 포트폴리오 핵심 내용 |
|---|---|
| 문제 | 클래스 간 최대 약 1,000배 불균형을 가진 웨이퍼맵 9-class 분류 |
| 모델 | 64×64 CNN과 결함 밀도·방향성 등 공정 파생변수를 결합한 Hybrid CNN |
| 실험 설계 | 파생변수×증강 2×2 ablation, Train/Val/Test 분리, Grad-CAM |
| 대표 성능 | IID 무작위 holdout Macro F1 0.885 / class-capped 신규 lot holdout 0.721 |
| 핵심 판단 | 같은 분포 성능과 신규 lot 일반화 성능을 구분하고, 배치 드리프트를 평가 설계에 반영 |

---

## 이 프로젝트가 푸는 문제

웨이퍼 한 장에는 수백~수천 개의 칩(다이)이 배열되어 있고, 검사 후 "이 칩은 정상/불량"이라는 결과가 웨이퍼 전체를 하나의 지도(맵)처럼 나타냅니다. 불량 칩들은 무작위로 흩어져 있기보다 **특정 모양**(패턴)을 이루는 경우가 많고, 그 모양마다 원인이 다릅니다 (예: 가장자리에 몰리면 장비 정렬 문제, 긁힌 자국 모양이면 이송 중 스크래치). 이 패턴을 사람이 눈으로 하나하나 분류하는 대신, **이미지를 보고 자동으로 패턴을 분류하는 모델**을 만드는 것이 이 프로젝트의 목표입니다.

---

## 전체 진행 순서

```
1단계. 데이터를 뜯어본다 (EDA)      →  라벨 비율, 클래스 불균형, 웨이퍼 크기 편차 파악
2단계. 이미지 전처리                →  제각각인 웨이퍼 크기를 통일
3단계. CNN 모델 학습 및 평가         →  9개 클래스(정상 + 결함 8종) 분류
4단계. 파생변수를 추가로 설계·검증    →  CNN이 놓치는 정보를 보완할 수 있는지 실험
5단계. 데이터 증강 적용               →  소수 클래스 샘플 부족을 회전·반전으로 보완
6단계. 운영 환경을 가정해 재검증       →  lot(생산 순서) 기준 분할로 다시 평가
7단계. 개선 효과를 통계적으로 검증    →  Train/Val/Test 분리 + 2x2 조합 + 신뢰구간
7-1단계. lot 기준으로 다시 3-way 분리  →  신규 lot holdout 성능 측정
8단계. 모델이 어디를 보고 판단했는지 확인  →  Grad-CAM으로 CNN 내부 들여다보기
```

## 1단계. EDA — 무엇을 확인했는가

**① 라벨이 있는 데이터는 전체의 21%뿐입니다.** 81만 장 중 17만 장(21.3%)만 사람이 결함 유형을 확인해 라벨을 붙여놨고, 나머지는 라벨이 없습니다. 그래서 학습에는 라벨이 있는 172,950장만 사용했습니다.

**② 클래스 불균형이 매우 심합니다.** 라벨이 있는 데이터 중에서도 "정상(none)"이 147,431장(85%)으로 대부분이고, 가장 희귀한 클래스인 "Near-full"(웨이퍼 전체가 불량인 경우)은 149장(0.09%)뿐입니다. 정상과 가장 희귀한 결함 사이의 비율 차이가 **거의 1,000배**입니다.

**③ 웨이퍼 이미지 크기가 다 다릅니다.** 웨이퍼맵 346가지의 서로 다른 크기(가로 3~204, 세로 15~212)로 저장되어 있어, 모델에 넣기 전에 크기를 통일하는 과정이 필요했습니다.

**④ 클래스별로 패턴이 실제로 육안으로도 뚜렷하게 다릅니다.** 아래는 클래스별 샘플 이미지입니다 — 파란색은 정상 칩, 빨간색은 불량 칩입니다. Center는 중앙에, Edge-Ring은 테두리를 따라, Scratch는 가늘고 긴 줄무늬로 나타나는 걸 볼 수 있습니다.

## 2단계. 전처리 — 크기를 어떻게 통일했는가

웨이퍼맵은 "0=칩 없음, 1=정상 칩, 2=불량 칩"이라는 **범주형 값**으로 이루어져 있어서, 사진처럼 부드럽게 리사이즈(보간)하면 이 값들이 뭉개져 의미가 왜곡됩니다. 그래서 **최근접 이웃(nearest-neighbor) 방식**으로 64×64 크기로 통일해 범주형 값을 그대로 보존했습니다.

또한 라벨이 있는 데이터도 클래스별로 불균형이 심해서(정상 147,431장 vs Near-full 149장), 클래스마다 **최대 2,000장으로 상한을 두고** 그보다 적은 클래스는 있는 만큼 전부 사용하는 방식으로 학습셋을 구성했습니다 (최종 학습에 사용한 이미지 12,763장).

---

## 3단계. CNN 모델 — 어떻게 학습했고 결과는 어땠는가

작은 CNN(합성곱 3층 + 완전연결 2층) 구조를 CPU 환경에서 15 epoch 학습시켰습니다 (총 학습 시간 약 3.7분). 클래스 불균형을 보정하기 위해 클래스별 가중치도 함께 적용했습니다.

### 결과

| 지표 | 값 |
|---|---|
| 전체 정확도 (Accuracy) | **80.1%** |
| Macro F1 (클래스 평균) | **0.80** |
| Weighted F1 | 0.79 |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/05_confusion_matrix.png" width="560" alt="혼동행렬">

클래스별로 보면 편차가 큽니다. Edge-Ring(0.95), Center(0.93)처럼 모양이 뚜렷한 패턴은 잘 맞히지만, **Scratch는 F1 0.37로 유독 낮았습니다.** 실제 Scratch 웨이퍼 중 상당수가 "정상"이나 "Loc"으로 잘못 분류됐습니다.

## 4단계. 파생변수 — CNN인데도 직접 변수를 만들 필요가 있었는가

이미지를 다루는 CNN은 **특징을 스스로 학습**하기 때문에, 보통은 사람이 변수를 따로 설계할 필요가 없다고 봅니다. 그래서 처음에는 파생변수 없이 진행했습니다. 그런데 3단계에서 Scratch 성능이 유독 나쁜 이유를 파고들다가, 데이터에서 이런 사실을 발견했습니다.

**Scratch의 "불량 칩 비율"이 정상 웨이퍼보다도 오히려 낮습니다** (Scratch 10.1% vs 정상 10.6%). Scratch는 가늘고 긴 줄 하나라서 불량 칩 개수 자체가 매우 적고, 게다가 64×64로 축소하는 과정에서 그 얇은 선이 뭉개져 CNN이 "그냥 정상 웨이퍼"로 착각하기 쉬웠던 것입니다.

그래서 **원본 해상도에서 직접 계산한 8개 파생변수**를 만들어 CNN에 함께 넣어봤습니다:
- 불량 칩 밀도, 중심으로부터의 평균 거리와 편차(Center/Edge 구분용)
- 불량 위치의 산포도, 특정 행·열에 몰린 정도(Scratch의 선형성 포착용)
- 웨이퍼 전체 크기, 가로세로 비율

### 검증 결과 — 실제로 효과가 있었습니다

동일한 조건에서 파생변수만 넣고 빼서 비교했습니다.

| 지표 | CNN만 | CNN + 파생변수 | 변화 |
|---|---|---|---|
| Macro F1 | 0.790 | **0.844** | **+0.053** |
| 정확도 | 80.2% | **83.5%** | +3.3%p |
| **Scratch F1** | 0.369 | **0.596** | **+0.227** |
| Near-full F1 | 0.811 | **0.968** | +0.157 |
| Loc F1 | 0.671 | 0.708 | +0.037 |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/07_derived_feature_comparison.png" width="640" alt="파생변수 유무에 따른 클래스별 F1 비교">

가장 어려웠던 **Scratch에서 F1이 0.37 → 0.60으로 크게 올랐고**, 전체 성능도 의미 있게 개선됐습니다.

**여기서 얻은 인사이트**: "딥러닝은 알아서 특징을 학습하니까 사람이 변수를 만들 필요가 없다"는 통념이 항상 맞는 것은 아닙니다. **전처리 과정에서 정보가 손실되는 경우(여기서는 이미지 축소로 얇은 선이 뭉개진 것), 원본에서 직접 계산한 변수를 넣어주면 그 손실을 보완할 수 있습니다.** 이는 데이터를 눈으로 들여다보는 EDA 없이는 발견하기 어려운 개선점이었습니다.

## 5단계. 데이터 증강 — Scratch를 한 번 더 개선할 수 있는가

파생변수로 Scratch F1이 0.60까지 올랐지만 여전히 다른 클래스보다 낮았습니다. 남은 원인은 단순합니다 — **Scratch는 학습 데이터가 원래 적습니다**(1,193장, 정상의 1/120 수준). 새 데이터를 구할 수는 없지만, 웨이퍼맵에는 활용할 수 있는 성질이 하나 있습니다: **회전시키거나 좌우로 뒤집어도 결함의 종류는 바뀌지 않습니다.** Center를 90도 돌려도 여전히 Center이고, Scratch를 뒤집어도 여전히 Scratch입니다.

이 성질을 이용해 학습 데이터가 적은 5개 클래스(Scratch, Random, Donut, Near-full, Loc)만 회전 4방향 × 좌우반전으로 최대 8배까지 늘렸습니다. **평가 데이터에는 증강을 적용하지 않고, 증강도 train 분할 이후에만 수행**해 데이터 누수를 방지했습니다.

> 참고로 이 증강은 "결함 유형 분류"라는 이 프로젝트의 목표를 전제로 한 것입니다. 실제 웨이퍼 위치(방향)가 공정 진단에 의미를 갖는 다른 목적(예: 특정 장비 방향과 결함의 상관관계 분석)이라면, 회전·반전으로 방향 정보를 지워버리는 이 증강은 적절하지 않을 수 있습니다.

### 결과 — Scratch가 한 번 더 크게 개선됐습니다

| 지표 | 증강 전 | 증강 후 | 변화 |
|---|---|---|---|
| Macro F1 | 0.840 | **0.882** | **+0.042** |
| 정확도 | 83.3% | **86.6%** | +3.4%p |
| **Scratch F1** | 0.609 | **0.750** | **+0.141** |
| Loc F1 | 0.680 | 0.768 | +0.088 |
| Random F1 | 0.888 | 0.946 | +0.059 |
| Donut F1 | 0.878 | 0.947 | +0.070 |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/08_augmentation_comparison.png" width="640" alt="증강 유무에 따른 클래스별 F1 비교">

증강을 적용한 5개 클래스가 전부 개선됐고(Edge-Loc처럼 증강하지 않은 클래스는 거의 변화 없음), 특히 **Scratch는 파생변수 단계(0.37→0.60)에 이어 이번에도 가장 크게 개선**되어 0.60에서 0.75까지 올랐습니다. 하나의 원인(샘플 부족)에 두 가지 서로 다른 해법(정보 보완용 파생변수, 데이터 양 자체를 늘리는 증강)을 각각 검증하며 순차적으로 성능을 끌어올린 과정입니다.

## 6단계. 운영 환경을 가정해 재검증하기 (lot 순서 분할)

제조 데이터는 시간이 지나며 공정 조건이나 장비 상태가 바뀌는 경우가 흔합니다. 그런데 지금까지는 전부 무작위 분할로만 평가했습니다 — "무작위로 섞어서 평가한 성능은 실제 배포 상황(과거로 학습해서 미래를 예측)과 다를 수 있다"는 위험을 점검하지 않은 셈입니다. WM-811K에는 타임스탬프가 없지만, `lotName`이 `lot1`, `lot2`, ... 순번으로 되어 있어 **생산 순서의 근사치**로 쓸 수 있습니다. 이를 이용해 같은 위험이 있는지 직접 확인했습니다.

### 발견 — 예상보다 훨씬 극단적인 드리프트가 있었습니다

라벨된 웨이퍼를 lot 순서로 10구간으로 나눠서 불량 비율을 보니:

| 구간 | 불량 비율 |
|---|---|
| 초반 20%(lot 순서 1~2구간) | **약 51%** |
| 나머지 80%(3~10구간) | 약 3~10% |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/16_lot_drift.png" width="640" alt="lot 순서별 불량 비율">

**초반 lot에서는 웨이퍼 절반이 불량이었는데, 이후로는 5~10% 수준으로 뚝 떨어집니다.** 라벨링 초기에 불량 사례를 의도적으로 더 많이 수집했거나, 초기 공정이 실제로 불안정했을 가능성이 있습니다 — 어느 쪽이든, 지금까지의 무작위 분할 실험은 이 초반 구간의 극단적인 불량 사례들과 나머지 안정 구간을 마구 섞어서 학습·평가해왔다는 뜻입니다.

### lot 순서 그대로 재검증한 결과

**train은 lot 순서 앞 80%, test는 뒤 20%로 나눴습니다** (train: lot1~45283, test: lot45284~47542 — 같은 lot이 train/test 양쪽에 걸치지 않도록 "고유 lot 개수" 기준으로 나눴습니다). 이렇게 나누고, 4단계의 파생변수 CNN을 그대로 다시 학습·평가했습니다. test 쪽은 클래스당 최대 500장까지만 쓰도록 상한을 뒀는데(계산량 제어 목적), 500장 미만인 클래스는 그 구간에 실제로 존재하는 만큼만 쓰고 그 이상은 늘리지 않았습니다 — 다만 이 상한 때문에 "none"처럼 원래 압도적으로 많은 클래스도 500장으로 잘려, **이 test set의 클래스 비율이 실제 생산 현장의 클래스 비율(불량 대부분이 5% 미만)을 그대로 반영하지는 않습니다.** 즉 아래 Accuracy는 "실전 배포 시의 정확도"로 그대로 읽으면 안 되고, Macro F1(클래스 비율에 영향받지 않는 지표)을 중심으로 봐야 합니다.

| 지표 | 무작위 분할 (기존 보고) | lot 순서 분할 (class-capped holdout) |
|---|---|---|
| Macro F1 | 0.844 | **0.603** |
| Accuracy | 83.5% | 56.9% |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/17_lot_split_comparison.png" width="480" alt="무작위 분할 vs lot 순서 분할 비교">

**Macro F1이 0.84 → 0.60으로 확실히 떨어집니다.** 클래스별로 보면 Scratch(0.30), Edge-Ring(0.37)처럼 원래도 까다롭거나 이 구간에서 표본 비율이 달라진 클래스가 lot 분할에서 더 크게 무너지고, Near-full(0.93)처럼 패턴이 뚜렷한 클래스는 여전히 잘 맞습니다.

> **버그 수정 내역**: 이 실험의 최초 구현은 "전체 웨이퍼 행(row) 개수의 80%"를 split 경계로 잘랐는데, 이는 "고유 lot 개수"가 아니라 "웨이퍼 개수" 기준이라 경계에 걸친 lot 하나가 train과 test 양쪽에 나뉘어 들어가는 lot 누수가 있었습니다(실제로 이전 버전은 lot 46088이 train 범위 끝과 test 범위 시작에 동시에 걸쳐 있었습니다). 고유 lot 목록을 먼저 정렬한 뒤 lot 단위로 80/20을 나누도록 수정했고, 위 수치는 수정된 버전의 결과입니다.

### 인사이트

이 점검은 프로젝트를 처음 마무리할 때는 빠져 있다가, 나중에 되짚어보고서야 찾아낸 것입니다. 실제로 fab 데이터는 시간·로트에 따른 드리프트가 흔하다는 걸 감안하면, **제조 데이터 프로젝트를 시작할 때는 "시간/생산순서 기준 분할"을 EDA 체크리스트에 기본으로 넣어야 한다**는 게 이번에 얻은 가장 중요한 교훈입니다.

## 7단계. 개선 효과가 정말 유의미한지 통계적으로 검증하기 (Train/Val/Test 3-way 분리)

4~5단계에서 "파생변수로 +0.05, 증강으로 +0.04 개선됐다"고 보고했는데, 이 숫자들이 서로 다른 실행에서 나온 데다가, 그 차이가 우연(노이즈)인지 실제 개선인지 확인하지 않은 채였습니다. 또한 "증강만 넣고 파생변수는 뺐을 때" 조합 하나가 실험에서 빠져 있었습니다.

처음엔 네 조합(아무것도 안 함 / 파생변수만 / 증강만 / 둘 다)을 동일한 test set에서 비교하고, 그중 가장 높은 조합을 그대로 "최종 성능"으로 보고했습니다. 그런데 이 방식에는 문제가 있습니다 — **4개 조합 중 가장 잘 나온 걸 골라서 그 test 점수를 최종 성능이라고 하면, test set이 사실상 모델을 고르는 데도 쓰인 셈**이 되어 보고된 숫자가 운 좋게 부풀려질 위험이 있습니다(여러 후보 중 최댓값을 취하는 데서 오는 선택 편향). 그래서 다음과 같이 다시 구성했습니다.

1. 데이터를 **train(60%) / validation(20%) / test(20%)** 로 나눕니다.
2. 네 조합의 비교와 "어느 조합이 최선인가"의 결정은 **validation set에서만** 합니다 — 이 단계에서 test set은 전혀 보지 않습니다.
3. validation에서 최선으로 확인된 조합만 **train+validation으로 다시 학습**시켜, **test set에서 딱 한 번** 평가합니다. 이 test 점수만 "최종 성능"으로 보고합니다.

### 1단계 결과 — validation 기준 조합 비교 (모델 선택용)

| 조합 | Macro F1 (95% 신뢰구간) |
|---|---|
| 아무것도 안 함 | 0.799 (0.783~0.814) |
| 파생변수만 | 0.830 (0.814~0.846) |
| 증강만 | 0.802 (0.787~0.817) |
| **파생변수 + 증강** | **0.871 (0.858~0.885)** |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/23_train_val_test_evaluation.png" width="640" alt="Val 기준 조합 비교 vs 최종 test 평가">

이전 실험과 마찬가지로 **증강 단독(+0.003)보다 파생변수 단독(+0.031)의 효과가 이번엔 더 컸고**, 둘을 같이 쓴 조합이 가장 좋았습니다 — 이 validation split에서 "파생변수+증강" 조합의 신뢰구간(0.858~0.885)이 나머지 세 조합의 신뢰구간보다 확연히 높은 범위에 있었습니다. (다만 이건 각 조합의 개별 신뢰구간을 나열해서 비교한 것이고, "두 조합 간 차이"를 직접 검정한 delta 신뢰구간을 계산한 것은 아니라서 — 그 방식은 아래 `ablation_with_ci.py` 섹션에서 별도로 사용했습니다 — "통계적으로 유의미하다"고 단정하기보다는 "이 정도로 뚜렷한 차이였다"는 수준으로 읽는 게 정확합니다.) 정확한 순위나 각 단독 효과의 크기는 어떤 20%가 test로 빠졌는지에 따라 조금씩 달라질 수 있다는 점도 이번 재구성으로 함께 확인했습니다 — 다만 "파생변수+증강이 최선"이라는 결론 자체는 두 번의 독립적인 실행(이전 실험, 이번 validation) 모두에서 일관됩니다.

### 2단계 결과 — 최종 성능 (test에서 딱 한 번 평가)

validation에서 최선으로 확인된 "파생변수 + 증강" 조합만 train+validation(36,880장, 증강 포함)으로 다시 학습시켜, 지금까지 한 번도 보지 않은 test set(2,553장)에서 평가했습니다.

| 지표 | 값 |
|---|---|
| **Macro F1** | **0.885 (95% CI 0.868~0.900)** |
| Accuracy | 88.4% |

이전에 "test 재사용" 방식으로 보고했던 0.893보다 소폭 낮지만(선택 편향을 제거한 만큼 자연스러운 결과), 여전히 두 방법을 합친 조합이 확실히 더 낫다는 결론은 그대로 유지됩니다. 클래스별로도 Scratch F1이 0.78까지 올라 4~5단계보다 한 번 더 개선됐습니다(더 많은 학습 데이터로 재학습한 효과).

> **이 0.885는 "신규 lot 일반화 성능"이 아닙니다.** 위 train/val/test 분리는 클래스별 상한을 둔 subset을 **웨이퍼 단위로 무작위** 60/20/20 분할한 것이라, 같은 lot의 웨이퍼가 train/validation/test 세 곳에 나뉘어 들어갈 수 있습니다. 6단계에서 이미 확인했듯 lot 순서에 따라 불량 비율이 극단적으로 다르므로(초반 lot 약 50% vs 나머지 5~10%), 같은 lot이 여러 split에 섞이면 "새 lot에서도 잘 되는가"를 실제보다 낙관적으로 보여줄 수 있습니다. **0.885는 "같은 분포 안에서 무작위로 나눴을 때의 패턴 분류 성능"으로 읽어야 하고, 신규 lot 성능은 아래 7-1단계의 lot 단위 분리 결과를 봐야 합니다.**

> **신뢰구간의 한계**: 위 신뢰구간은 "이 test set을 다시 뽑았다면 얼마나 흔들렸을까"만 반영합니다. 다른 랜덤 시드로 모델을 다시 학습했을 때의 변동이나, 데이터를 다시 수집했을 때의 변동까지는 포함하지 않습니다.

### 7-1단계. lot 기준 Train/Val/Test — 신규 lot 일반화 성능

바로 위에서 밝혔듯, 7단계의 0.885는 웨이퍼를 무작위로 섞어 나눈 것이라 "신규 lot에 대한 일반화 성능"으로 쓸 수 없습니다. 6단계(`lot_split_validation.py`)는 사전에 고정한 단일 모델을 lot 기준 train/test 2-way로 평가한 진단 실험이어서, validation에서 조합을 선택한 뒤 독립 test에서 확인하는 절차는 없었습니다. 이를 보완해 **고유 lot을 앞 60%/다음 20%/마지막 20%로 나누고, validation에서만 조합을 고른 뒤 test에서 딱 한 번 평가**했습니다. train은 클래스당 최대 2,000장과 증강을 적용했고, validation/test는 증강 없이 클래스당 최대 500장을 고정 시드로 무작위 추출했습니다. 따라서 이 평가는 lot은 독립적으로 분리하지만 클래스 비율은 실제 생산 분포와 다릅니다.

train은 lot1~42995(6,457개 lot), validation은 lot42996~45283(2,152개 lot), test는 lot45284~47542(2,153개 lot)입니다.

**1단계: validation(신규 lot) 기준 조합 비교**

| 조합 | Macro F1 |
|---|---|
| 아무것도 안 함 | 0.706 |
| 파생변수만 | 0.715 |
| 증강만 | 0.704 |
| **파생변수 + 증강** | **0.785** |

무작위 분할(7단계)에서와 마찬가지로 "파생변수+증강"이 가장 우수했습니다. 다만 절대 수치 자체는 무작위 분할 validation(baseline 0.799)보다 전반적으로 낮습니다(baseline 0.706) — 신규 lot에서는 애초에 문제 자체가 더 어렵다는 뜻입니다.

**2단계: 최종 test(더 새로운 lot) 평가 — 딱 한 번**

validation에서 확정된 "파생변수+증강" 조합을 train+validation(47,516장, 증강 포함)으로 재학습해, 지금까지 한 번도 보지 않은 test lot(2,892장)에서 평가했습니다.

| 지표 | 값 |
|---|---|
| **Macro F1** | **0.721** |
| **lot-cluster bootstrap 95% CI** | **0.695~0.746** |
| Accuracy | 71.0% *(class-capped subset 참고값)* |

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/24_lot_train_val_test_evaluation.png" width="640" alt="lot 기준 Val 조합 선택 vs 최종 lot-test 평가">

**0.721을 이 프로젝트의 신규 lot holdout 대표 수치로 사용합니다.** 다만 클래스당 최대 500장으로 제한한 평가셋이므로 생산 분포의 Accuracy가 아니라 Macro F1 중심으로 해석합니다. 신뢰구간은 같은 lot 안의 웨이퍼를 독립 표본으로 취급하지 않도록 **lot 단위 cluster bootstrap**으로 계산했습니다. 저장된 최종 모델을 재학습하지 않고 다시 추론해 점 추정치 0.7207이 동일함을 확인한 뒤, 기존 wafer bootstrap 구간을 0.6947~0.7456으로 교체했습니다. 6단계의 2-way 진단 결과(0.603), 7단계의 IID 성능(0.885)과 함께 보면 평가 질문의 차이가 분명해집니다.

| 평가 방식 | Macro F1 | 의미 |
|---|---|---|
| 웨이퍼 무작위 3-way(7단계) | 0.885 | 같은 분포 안에서 패턴을 얼마나 잘 배우는가 |
| lot 2-way(6단계) | 0.603 | 사전에 고정한 모델의 신규 lot 진단 결과 |
| **lot 3-way(7-1단계)** | **0.721** | **validation 선택 후 독립 신규 lot에서 측정한 대표 수치** |

클래스별로는 Near-full(0.93), Random(0.85), Center(0.83)처럼 패턴이 뚜렷한 클래스는 비교적 높았고, Edge-Ring(0.60)·Donut(0.54)·Scratch(0.60)는 낮았습니다. 포트폴리오에서는 **0.885를 동일 분포 성능, 0.721을 class-capped 신규 lot holdout 성능**으로 함께 제시합니다.

## 8단계. 모델이 어디를 보고 판단했는지 확인하기 (Grad-CAM)

지금까지는 F1 점수로만 성능을 봤는데, 점수가 좋다고 해서 모델이 실제로 올바른 이유로 맞히고 있다는 보장은 없습니다. CNN이 예측할 때 이미지의 어느 영역을 실제로 "보고" 있었는지를 히트맵으로 보여주는 **Grad-CAM**으로 이걸 직접 확인했습니다.

> **한계**: 최종 모델은 CNN(이미지) 경로와 파생변수 경로가 분류기 직전에 합쳐지는 하이브리드 구조입니다. Grad-CAM은 CNN 경로에만 걸려 있어서, **파생변수가 판단에 얼마나 기여했는지는 이 히트맵에 나타나지 않습니다.** 즉 아래 시각화는 "이미지만 봤을 때 모델이 어디에 반응하는가"이지, 모델의 최종 판단 근거 전체를 설명하는 것은 아닙니다. 또한 클래스별 예시는 **정확히 분류된 사례들 중에서** 무작위로 뽑았습니다 — 우연히 보기 좋은 사례만 고른 것이 아님을 밝혀둡니다.

### 클래스별로 실제 결함 위치를 보고 있었습니다

<img src="https://raw.githubusercontent.com/ojineeee/WM811K_wafer_defect_classification/main/results/figures/21_grad_cam_by_class.png" width="640" alt="클래스별 Grad-CAM">

7-1단계에서 확정한 최종 모델(lot 기준 train+val로 재학습, "파생변수+증강" 조합)로, 9개 클래스 각각에서 정확히 맞힌 사례를 무작위로 하나씩 뽑아 히트맵을 그려봤습니다(임의로 보기 좋은 사례를 고른 게 아님을 밝혀둡니다). Random은 웨이퍼 전체에 걸쳐 넓게 반응했고, Near-full도 거의 전체 영역에 반응했으며, Loc은 한 지점에 뭉친 국소 반응, Edge-Loc·Edge-Ring은 테두리 근처에 반응했습니다 — 대체로 각 패턴의 정의와 일치합니다. 이번에 뽑힌 Scratch 사례는 선 전체가 아니라 한 지점의 국소적인 반응에 그쳤습니다. `none`(정상) 사례에서도 일부 국소적으로 강하게 반응하는 지점이 있었는데, 이건 왜 그런지 이번 분석만으로는 확정할 수 없어 열린 질문으로 남겨둡니다. (위에서 밝혔듯, 파생변수 경로가 판단에 기여한 부분은 이 히트맵에 나타나지 않습니다.)

### Scratch를 더 깊게 파봤습니다 — 왜 여전히 제일 어려운 클래스인지

Scratch 사례 4개를 무작위로 더 뽑아봤습니다. 결과가 섞여 있었습니다 — **정답인 두 건(#2539, #2688)은 대각선 방향으로 국소 반응이 늘어서 있어 선의 일부 구간은 따라갔지만 선 전체를 깔끔하게 추적하지는 못했고, 정답인 #2844는 선이 아니라 웨이퍼 여러 지점에 흩어진 반응을 보였고, 오답(#2762, 예측: none)은 선이 아닌 국소 지점 하나에 반응**하고 있었습니다. 4건 중 선 전체를 뚜렷하게 추적한 사례는 없었습니다 — lot 기준으로 재학습한 모델에서도 같은 패턴(부분적/국소적 단서 의존)이 재현됩니다.

**여기서 얻은 인사이트**: Scratch의 F1이 다른 클래스보다 계속 낮은 이유(lot 기준 최종 모델 기준 0.60)가 단순히 "샘플이 적어서"만은 아니라는 걸 확인했습니다. **정답을 맞힌 경우에도 모델이 매번 선 전체를 근거로 판단하는 게 아니라, 대부분 선의 일부 구간이나 국소적인 단서만으로 판단하고 있었습니다.** 이는 정확도 숫자만으로는 볼 수 없었던 발견이고, 다음 개선 방향(선 형태 검출에 특화된 전처리·구조)이 왜 필요한지에 대한 훨씬 구체적인 근거가 됩니다.

## 포트폴리오 핵심 역량

- **이미지 데이터 전처리**: 크기가 제각각인 데이터를 의미를 보존하며 통일하는 방법(범주형 데이터에는 nearest-neighbor 리사이즈가 필요하다는 것)
- **극심한 클래스 불균형 대응**: 1,000배 차이 나는 불균형을 서브샘플링 + 클래스 가중치로 함께 보정
- **CPU 환경에서의 현실적인 딥러닝 설계**: GPU 없이도 데이터 규모·이미지 크기·모델 구조를 조절해 몇 분 안에 실제로 쓸만한 결과를 내는 경험
- **원인 분석에서 개선으로 이어가는 과정**: 성능이 나쁜 클래스를 그냥 "어렵다"고 남기지 않고, 왜 어려운지 데이터에서 원인(불량 밀도가 정상보다 낮음)을 찾아내 파생변수로 해결하고 실험으로 검증
- **딥러닝에 대한 통념을 데이터로 검증**: "CNN은 특징을 알아서 학습하니 파생변수가 불필요하다"는 통념을 실제 실험으로 확인해, 이 경우엔 해당하지 않음을 수치로 입증
- **결과를 정직하게 해석하는 태도**: 전체 정확도만 보고하지 않고, 어떤 클래스가 왜 어려운지까지 원인을 분석해서 기록
- **평가 방식 자체를 의심하고 재검증하는 습관**: 무작위 분할 성능을 그대로 믿지 않고, `lotName`을 생산 순서 proxy로 활용한 재검증을 스스로 찾아내 수행 — 그 결과 Macro F1이 0.84→0.60으로 떨어지는 것을 확인하고 정직하게 보고
- **개선 효과의 불확실성 정량화**: 네 조합을 동일 조건에서 재학습하고, lot holdout에서는 lot 단위 cluster bootstrap으로 같은 배치 내 상관을 반영
- **모델 선택과 최종 평가를 분리하는 습관**: 처음엔 네 조합을 같은 test set에서 비교하고 그중 최고를 그대로 "최종 성능"이라 보고했는데, 이 방식이 test set을 모델 선택에도 써버리는 선택 편향을 만들 수 있다는 걸 인지하고 train/validation/test 3-way로 재구성 — validation에서만 조합을 고르고, test는 최종 모델을 딱 한 번 평가하는 데만 사용
- **자신이 짠 검증 코드의 버그를 스스로 찾아 고친 경험**: lot 순서 분할 스크립트가 "행 개수" 기준으로 나뉘어 있어 특정 lot 하나가 train/test 양쪽에 걸쳐 들어가는 누수가 있다는 걸 뒤늦게 발견 — "고유 lot 개수" 기준으로 고쳐서 재실행하고, 수치가 어떻게 바뀌었는지도 투명하게 기록
- **모델 해석(Explainability)의 한계까지 함께 밝히는 태도**: Grad-CAM으로 모델이 각 클래스를 판단할 때 실제로 이미지의 어느 영역을 보는지 확인하면서도, 하이브리드 모델의 파생변수 경로는 이 기법으로 설명되지 않는다는 것과, 정확히 분류된 사례들 중에서도 무작위로 뽑아야 "우연히 보기 좋은 사례"로 편향되지 않는다는 것까지 함께 명시
- **"성능이 무엇을 측정한 것인지" 끝까지 따져보는 습관**: 7단계의 train/val/test 3-way 분리가 여전히 웨이퍼 단위 무작위 분할이라 lot 누수가 남아있다는 걸 인지하고, 6단계(lot 기준 분할)와 7단계(모델 선택/평가 분리)의 방법론을 합쳐 lot 기준 3-way 분리를 다시 구현 — "같은 분포에서의 성능(0.885)"과 "신규 lot 일반화 성능(0.721)"을 명확히 구분해서 보고

## 한계점

- CPU 환경 제약으로 클래스당 최대 2,000장만 사용했습니다. 전체 라벨 데이터(17만 장)를 다 쓰고 GPU로 학습하면 특히 Scratch 같은 소수 클래스에서 성능이 더 개선될 가능성이 있습니다.
- 라벨이 없는 79%의 데이터는 이번 프로젝트에서 활용하지 않았습니다. 준지도학습(semi-supervised learning)으로 라벨 없는 데이터까지 활용하는 것이 다음 개선 과제입니다.
- 64×64로 축소하면서 생기는 정보 손실을 파생변수로 상당 부분 보완했지만, 애초에 더 큰 해상도(예: 96×96)로 학습하면 어떻게 달라지는지는 이번에 비교하지 못했습니다.
- Scratch F1이 다른 클래스(대부분 0.85 이상) 대비 여전히 낮습니다. **8단계 Grad-CAM 분석에서 그 이유의 일부를 확인했습니다** — 정답을 맞힌 경우에도 모델이 항상 실제 선을 근거로 판단하지는 않았습니다. 선(line) 형태 검출에 특화된 기법(Hough 변환 등)을 추가로 시도해볼 여지가 있습니다.
- **신규 lot에 대한 일반화 성능(7-1단계, Macro F1 0.721)은 같은 분포 성능(0.885)보다 확실히 낮습니다.** 특히 Edge-Ring(0.60)·Donut(0.54)·Scratch(0.60)처럼 무작위 분할에서는 잘 되던 클래스도 신규 lot에서는 크게 하락합니다. 지금 상태로는 신규 lot에 대한 일반화가 무작위 분할 성능만큼 보장되지 않습니다.
- 모델 구조(CNN)를 단 하나만 사용했습니다. 파생변수만으로 classical ML(Random Forest 등)을 돌렸을 때와 비교해 CNN의 이미지 표현 학습이 실제로 얼마나 더 기여하는지는 검증하지 못했습니다.
- lot 순서가 왜 이렇게 극단적으로 드리프트하는지(라벨링 방식 때문인지 실제 공정 변화 때문인지)는 메타데이터만으로는 확정할 수 없어 추정에 머물렀습니다.
- 7단계 IID 평가는 웨이퍼 단위 bootstrap, 7-1단계 lot 평가는 lot 단위 cluster bootstrap을 사용합니다. 두 방식 모두 랜덤 시드를 바꿔 재학습했을 때의 변동까지는 반영하지 않습니다.
- 8단계 Grad-CAM은 최종 모델의 CNN(이미지) 경로만 설명합니다. 최종 모델은 파생변수를 함께 쓰는 하이브리드 구조라, 파생변수가 판단에 기여한 부분은 이 분석에서 확인할 수 없습니다.
- 7-1단계에서도 validation/test는 계산 시간 제어를 위해 클래스당 최대 500장 상한을 뒀습니다. 상한보다 적은 클래스는 그 lot 구간에 실제로 있는 만큼만 쓰지만, 상한보다 많은 클래스(none 등)는 여전히 500장으로 잘리므로 test set의 클래스 비율이 실제 생산 현장의 비율을 그대로 반영하지는 않습니다.
